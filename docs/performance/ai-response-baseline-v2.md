**No streaming exists in these paths.** They await `session.respond(...).content`, not a streaming API, and append a complete text or mapped preview afterward. First displayed assistant reply and complete displayed reply should coincide at the first rendered frame for that response today; still record separate endpoints so future streaming cannot change the denominator. Thinking and user echo are feedback, not first answer; a clarification question is a complete response for its own turn, not completion of the overall intent. For capture/plan, template text, preview and enabled action may appear in the same update but must be observed separately. There is no observable token-first latency in the current implementation.

Stage caps are not measurements or total response guarantees. An uncertain-intent turn may perform chat routing followed by kind and title steps; single-item kind and title caps are sequential, not one shared 8-second budget. Scheduling, mapping, persistence and rendering add time. Do not publish a sum of caps as measured latency.

## Cancellation, retry and MainActor hypotheses

- Each accepted send cancels the stored `captureTask`; asynchronous result handlers check `Task.isCancelled` before changing UI. No dedicated Stop or Retry control or automatic model retry was found. Resending is a new user turn and may supersede work. `onDisappear` closes Activity card records, but does not explicitly cancel `captureTask`; the separate SwiftUI `.task` handles prewarm.
- `ModelTimeout` and title refinement use checked continuations/one-shot locks and unstructured work/timer tasks. Timeout cancels the work task after resolving nil; caller cancellation is not explicitly forwarded through a cancellation handler. Multi-item `AICapture.withTimeout` drops late results but does not cancel the work task. Cancellation is cooperative: suppressed UI does not establish that generation stopped. Record timeout, cancellation, late completion and supersession separately; do not fix lifecycle behavior in the first measurement diff.
- Ask response tasks explicitly resume on MainActor. Context construction, regex routing, candidate collection, parser/mapping/list assignment, synchronous day planning, message/card JSON encoding and `ModelContext.save` are potential main-thread work. Awaiting a model does not prove generation runs on MainActor or blocks it. Profile execution/thread time only after baseline spans identify a dominant stage.
- `AskView` prewarms `Understanding` on opening; the prewarm session is not retained and uses kind instructions. Chat/title/multi-item/edit sessions are fresh. Whether prewarm benefits another session is unmeasured; do not call a first send “model cold” just because the process restarted.
- Hypotheses only: sequential kind/title generation may dominate eligible real-device capture; whole-history encode/save and candidate scans may dominate long-chat/large-agenda feedback; uncancelled late work may overlap a subsequent turn; title refinement may expose a gap between fast routing and ready preview. None justifies removal, caching, timeout reduction or guessed speedup before matched evidence.

## Context matrix, sampling and endpoint honesty

Keep these tracks separate:

1. **Simulator/local fallback:** `AICapture.isAvailable` explicitly false on simulator. `Understander` current main checks that before classification; title fallback executes locally. Chat is fallback; model-required edit reports unavailable; multi-item split flag is synthetic. Fake AlarmKit/Health and disabled sync are not physical integrations.
2. **Physical Apple Intelligence:** pending future owner-coordinated access, not performed or newly authorized by this research. Record device/OS/build, model availability reason, locale support, Apple Intelligence enabled/download state, prompt/schema/configuration SHA, token limits, actual model stage taken and thermal/load context. There is no remote service URL, network TTFT or cloud endpoint to benchmark in current source.
3. **Host logic/deterministic seams:** package tests exercise rules/mapping/injected generation and synthetic outputs. They prove selected semantics, not Foundation Models latency, UI rendering or durable saves.
4. **Storage:** default `-uiTesting` is in memory. A named `-uiTestingStore` file store plus fresh-context/relaunch reads is required for persisted item/thread/card/ledger observations. Successful SwiftData save is an API boundary; read-after-relaunch shows process persistence, not verified fsync or power-loss durability. Activity SQLite and EventKit/AlarmKit synchronization need separate completion evidence; sync-disabled runs cannot establish system-app propagation.

For **each journey/backend/build/configuration** collect raw n=3 process-cold/OS-warm first-send samples from three relaunches, and separately n=3 same-process warm samples after a defined untimed representative request. Use fresh/restored identical fixture/thread state for each sample; reset added items/plans outside the measured interval. Do not pool cold/warm or reuse a growing chat as “same workload.” Record Ask-open→send delay and prewarm start; default prewarm remains enabled. “Model cold” is unknown without platform evidence; never infer it from app termination. No reboot/cache purge. For multi-turn cases, keep within-journey context fixed and label each turn's cold/warm status.

Metadata: exact production SHA and instrumentation diff/hash, date/time/zone, build and optimization (`Debug -O` fixture-enabled track separate from Release), SDK/Xcode, device/runtime/UDID, store kind, fixture hash/counts, current thread length/context lengths, grants/Activity settings, sync state, model availability/result provenance, launch/prewarm/cache condition, thermal/host load and raw units. n=3 median + min/max/range; no p95, confidence interval, 3x or 10x claim from unmatched data. Cancellations/timeouts/errors are outcomes and remain in results, not discarded successful-sample filtering. Missing endpoint is missing, not zero.

Latency result register (all current values pending): send→feedback, send→first displayed answer, send→complete displayed answer, send→preview, send→enabled Add/Apply, Add/Apply→acknowledgement, Add/Apply→successful save, Add/Apply→relaunch-verified item + ledger persistence. Report proxy endpoints with their full proxy names; true display endpoints remain unmeasured if screen evidence is unavailable. Preview/action metrics are N/A for chat; commit metrics N/A before confirmation. Store human dwell separately.

Acceptance guards: correct conversational routing (including reported actions and explicit requests whose objects are questions); bounded same-thread context with no cross-thread/assistant-invented action; no writes before Add/Apply except explicit valid grants; alarm missing time disables Add; exact requested weekday set, date/time/repeat/type; names, negation, conditions, numbers and intent retained in title/notes; correct existing target and occurrence; meetings/deadlines fixed except explicit edits; pending previews survive chat; decided-card/thread restore and Undo remain correct; unavailable/timeout paths remain useful and honest. Speed cannot be purchased by deleting title refinement, returning an incomplete preview as complete, weakening assertions, shortening data or changing authorization.

Owner goals: first establish a matched baseline; required speed goal **baseline / 3**, stretch **baseline / 10** for each comparable latency endpoint. Immediate visible feedback **≤100 ms is aspirational**, independently of generation completion; it is not evidence that a complete model answer should take 100 ms. Track baseline, candidate, n/median/range, ratio, absolute gap, correctness result, limitations and next action for every context/endpoint. No gains are claimed in this source audit.
