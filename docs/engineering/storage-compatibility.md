# Today storage compatibility

Baseline: local commit `395376bb126fd7415ac6b44eee91b796eb8ca60c`. This contract supports reconstruction without silently resetting existing installations. Retain `Habit` and `LedgerEntry` in the SwiftData schema even though their features no longer write them. No Habits UI is authorized.

There are no explicit `@Relationship` declarations in these baseline models. Relationships still matter: `OneTask.listName` joins `OneList.name` (empty means Inbox); `ChatThread.itemsData` encodes final `PersistentIdentifier`s; cards carry item references; ledger `itemRef` encodes a persistent identifier; Undo uses UUID links; alarms have stable `alarmKitID`; sync uses EventKit external IDs. Do not replace these with newly generated IDs or fake strings during a real store upgrade.

Task/event `repeatRule` stores `RepeatRule.rawValue` (`daily`, `weekdays`, `weekly`, `monthly`, `yearly`, `weekly:2,4`); checklist UUIDs are embedded Codable values. Planned start and due are independent. `TaskSnapshot`, chat JSON and persistent-ID JSON use default JSONEncoder strategies (Date seconds since 2001), whereas share/widget JSON uses ISO8601 and Activity uses Unix milliseconds with independently persisted timezone minutes/local day. ISO8601 output loses fractional seconds in the baseline; preserving the existing whole-second representation is the measured contract, not subsecond fidelity.

## Executed disk characterization

Run [the standalone harness](../../tests/migration/README.md) for source hashes, generated old-writer artifacts and independent reader execution. Only synthetic data is used. The driver compiles unmodified selected baseline sources under module `MigrationDiskContract`; this module name is intentionally **not** a SwiftData identity claim.

The macOS harness actually writes, closes and reopens disk SQLite; verifies UID replay, order, exact snapshot bytes, content and Undo references, dates/timezone/day, checklist IDs, list name and recurrence strings; reads JSONL export and CSV quoted/newline fields; reads share and widget snapshots; parses extension-written JSONL and replays it without duplicate rows. Original fixture hashes must remain unchanged after verification.

Production `LedgerImport` is exercised with an incomplete first fetch, connection closure, and resumed import: partial copy must not set `ledger_migrated`; reopening recognizes the prior UUID; only verified completion sets the flag/session; the same launch cannot remove legacy rows. The test never removes legacy rows. This uses real disk Activity storage with plain `LegacyLedgerRow` input, not an actual old SwiftData fetch or abrupt process termination.

Production `ShareImport` is exercised across commit/failed acknowledgment and reopened receipt storage, then append-between-read-and-ack. The receipt adapter uses test-only Activity metadata, not production SwiftData. Existing `ShareImportDurabilityTests` already cover failed persistence, acknowledgment retry, Undo receipt retention, duplicate IDs and corrupt inbox retention; this lane adds reusable writer artifacts rather than duplicating that suite. It does not prove simultaneous multi-process file coordination.

A synthetic database with `user_version=999` must throw `newerSchema(999)` and retain its sentinel row. Harness failures preserve artifacts; neither deletion nor recovery/replacement is a passing result. This verifies the direct initializer; it does not claim `openOrRecover` is byte-preserving. Baseline recovery explicitly moves damaged database/sidecars aside and opens a new file, and must never be used to hide a failed migration acceptance test.

## Known baseline risk: outbox acknowledgment

Source inspection shows `ActivityCenter.importOutbox` calls `record`, `flush`, then `ActivityOutbox.remove(read.done)` without receiving persistence success. `ActivityRecorder.flush` catches insertion failures, retries in memory fewer than five times, and returns `Void`. Recording can also be unavailable or switched off. Therefore the app can remove durable outbox files before successful disk insertion; process exit can lose the memory retry. `ActivityOutboxImport.read` also marks a readable file done even if all its lines fail parsing. These are baseline behavior/risk findings, not verified durability guarantees or fixes in this test-only lane.

A future repair needs explicit durable-commit acknowledgment before file removal, a deliberate policy for paused categories, and malformed-line retention/quarantine rules. Acceptance must inject insert failure in the actual app import path, terminate/relaunch, and verify retained files/UIDs without loss. The standalone successful-insert replay check cannot close this gap.
